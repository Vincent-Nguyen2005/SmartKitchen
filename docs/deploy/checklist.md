# Production deploy checklist (Render)

For: Huy. Config: [`deploy/render.yaml`](../../deploy/render.yaml). Why Render: [decision.md](decision.md).
Env reference (placeholders only): [`deploy/env.production.example`](../../deploy/env.production.example).

## 0. Before you start

- [ ] `main` has the Sprint 4 PR merged and **CI / ci-success** is green on `main`.
- [ ] `pnpm check:infra` passes locally (only the gateway is public, secrets are not literal, Dockerfiles are non-root).
- [ ] You know the real client origins for `CORS_ORIGINS` (mobile web build / admin web), e.g. `https://app.example.vn`.
- [ ] You have an Expo access token (expo.dev → Account settings → Access tokens) if push should be real.
- [ ] You have an SMTP mailbox + app password for auth-service OTP emails.

## 1. Create the Blueprint

1. Render dashboard → **New → Blueprint** → connect GitHub repo `Vincent-Nguyen2005/SmartKitchen`, branch `main`.
2. **Blueprint Path:** `deploy/render.yaml`.
3. Review the plan: 1 web service (`smartkitchen-gateway`), 3 private services, 3 PostgreSQL databases, 2 env groups.
4. Render asks for every `sync: false` value. Enter:
   - gateway `CORS_ORIGINS` — the real origins, comma-separated (never `*`)
   - auth `CORS_ORIGIN`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM`
   - notification `EXPO_ACCESS_TOKEN`
5. `JWT_SECRET`, `INTERNAL_API_KEY` and `PARTNER_API_KEY` are generated by Render (`generateValue`). Do not type them.

## 2. First deploy

- [ ] Apply the Blueprint. Databases are created first, then the services build from their Dockerfiles.
- [ ] Each Prisma service runs `prisma migrate deploy` on start. In each service's **Logs**, look for `No pending migrations to apply` or `All migrations have been successfully applied`.
- [ ] Every service shows **Live**.
- [ ] Only `smartkitchen-gateway` has a public `*.onrender.com` URL. The private services show no public URL.

## 3. Smoke test (read-only)

```powershell
pnpm test:prod-smoke -BaseUrl https://smartkitchen-gateway.onrender.com -Origin https://app.example.vn -AllowDegraded
# same as: powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-prod-smoke.ps1 -BaseUrl ...
```
```bash
pnpm test:prod-smoke:bash https://smartkitchen-gateway.onrender.com https://app.example.vn --allow-degraded
```

Stage 1 needs `-AllowDegraded`, because stage-2 services are not deployed and `/api/health` answers 503 DEGRADED. The script checks: `/health` 200, `/api/health`, unknown route 404 JSON, no stack traces, internal routes hidden, forged `x-user-role` not trusted, invalid token 401, rate-limit headers present, and the CORS preflight for your origin (allowed) and for an unknown origin (refused).

## 4. Monitoring

- Render → each service → **Metrics / Logs**. Errors are single JSON lines (`"event": "request_error"`, `"health_monitor_*"`, `"report_notification_failed"`).
- Admin health dashboard (admin app → System health) or `GET /api/admin/health-monitor/status` with an ADMIN token.
- Render **Notifications** → email on deploy failure / service down.

## 5. Rotate secrets

| Secret | How | Effect |
|---|---|---|
| `PARTNER_API_KEY` | notification service → Environment → edit value (`openssl rand -hex 32`) → Save → redeploys | Partners must switch to the new key at the same time; old key stops working immediately |
| `INTERNAL_API_KEY` | Env group `smartkitchen-internal` → regenerate/edit → both admin and notification redeploy | A reporter notification sent during the redeploy may fail; resolutions still succeed (best effort) |
| `JWT_SECRET` | Env group `smartkitchen-jwt` → regenerate → auth and gateway redeploy | Every access token becomes invalid (users log in again); refresh tokens are opaque and unaffected |
| `EXPO_ACCESS_TOKEN`, `SMTP_PASS` | Service → Environment → edit | Next push / OTP email uses the new value |

## 6. Rollback

1. App problem: service → **Events** → previous successful deploy → **Rollback**.
2. Migrations are forward-only. If a deploy shipped a migration, the previous image must still work with the new schema (expand/contract). If it does not, or the data is damaged: database → **Recovery** (point-in-time / backup), then roll back the service.
3. Re-run the smoke test.

## 7. Go / no-go

- [ ] CI green on the commit being deployed
- [ ] All services Live; migrations applied without errors
- [ ] Only the gateway has a public URL; databases have no external access
- [ ] `CORS_ORIGINS` contains only real origins (no `*`); `TRUST_PROXY=true`
- [ ] `ENABLE_JOBS=true` only on the single notification and admin instance (`numInstances: 1`)
- [ ] Smoke test: 0 FAIL (degraded `/api/health` accepted only for stage 1)
- [ ] An admin account exists (role `ADMIN` in auth_db) for the admin screens
- [ ] Rollback path understood (section 6) and a database backup exists

**No-go** if any backend has a public URL: the header trust model (`x-user-role`) would let anyone become admin.
